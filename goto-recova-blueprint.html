4 Contratos de dados — o fio entre as telas e o motor

Por quê existe: cada número que aparece numa tela tem uma origem exata. Estes são os contratos que o backend entrega; se um campo mudar, a tela quebra de propósito (fail fast). Status: contrato-alvo a implementar (W08 pendente é parte disto).

▸ POST /recovery/parse — a frase vira requisitos + rota (alimenta Tela ②) 
{
  session_id: "sess_8f2",
  query: "vestido verde casamento até 200 reais",
  requirements: {
    hard:  [{attr: "price_max", value: 200}, {attr: "size", value: "M"}],   // inegociáveis
    soft:  [{attr: "color", value: "verde"}, {attr: "occasion", value: "casamento"}] // flexibilizáveis
  },
  route: "RECOVER",            // NATIVE_OK | RECOVER | CLARIFY
  clarify_question: null       // preenchido só na rota CLARIFY (1 pergunta, chips)
}
▸ POST /recovery/solve — os cartões com prova (alimenta Tela ③) 
{
  candidates: [
    { sku: "VD-SERENA-M", title: "Vestido Midi Serena · Verde Oliva",
      price: 189.00, strategy: "EXACT_ALTERNATIVE",          // 1 das 6 táticas
      proof: {color: true, occasion: true, price_max: true, stock: true},
      why: "O único verde disponível no seu orçamento — e é midi, tendência pra casamento.",
      recommended: true }
    // + VARIANT_RECOVERY (R$214, acima do teto) + BUNDLE_RECOVERY (R$168)
  ],
  fallback: null                // se vazio → strategy = "NO_VALID_RECOVERY" (Tela ⑦)
}
▸ Evento ORDER_PAID → ledger (gera o número da Tela ⑥) 
{
  event: "order.paid", order_id: "shp_1001",        // idempotency_key = order_id
  session_id: "sess_8f2",                          // liga o pedido à busca que falhou
  recovered: true,                                  // true se houve interação Recova na sessão
  amount: 189.00, currency: "BRL",
  hmac_verified: true, attempts: 1                 // attempts>1 = replay bloqueado
}
// → Firestore ledger (append-only): "R$ 512 recuperados hoje" soma estes eventos
▸ Config do lojista (versão) — alimenta Telas ⑪ e ⑫ 
{
  merchant_id: "aurora", version: 7,
  menu: [{id: "ocasioes", label: "👗 Ocasiões", enabled: true, order: 1} /*…*/],

7 Definition of Done por tela — "pronta" tem critério objetivo

Por quê existe: "acho que tá pronto" não existe aqui. Uma tela está pronta quando TODAS as caixas dela estão marcadas.

① Busca falha + oferta
  • Overlay aparece SOMENTE com zero_results && query≥3
  • Máx. 1 oferta por sessão (anti-spam)
  • Aparece < 200ms, sem esperar LLM
  • Nunca cobre nem bloqueia os best-sellers
② Leitura da busca
  • Chips = hard vs soft visível
  • Rotas coerentes com os exemplos do PLAN_FINAL
  • Nunca pede o que a frase já trouxe
③ Cartões
  • Todos os proof ✓ vêm do Solver (não decoram)
  • Preço/estoque = catálogo real
  • "Por quê" cita o motivo real da escolha
④ Conversa
  • Atributo novo → cartões atualizam sem reload
  • Máx. 3 refinamentos; depois decide ou encerra
⑤ Checkout + esteira
  • Pagamento simulado, ORDER_PAID REAL
  • HMAC verificado + idempotência testada (replay não conta 2×)
⑥ Painel
  • KPIs = soma do ledger (não mock fixo)
  • Lista de buscas falhas = OTel real
⑦ Honestidade
  • Aparece QUANDO strategy=NO_VALID_RECOVERY
  • Nunca mostra produto não aprovado
  • 2 saídas: alerta (C4) ou risco do usuário
⑧–⑩ Onboarding
  • 3 portas funcionam no demo (Shopify = fluxo mostrado)
  • 3 propostas de bot derivam do catálogo demo
  • Preview conversa com catálogo real
⑪–⑫ Dashboard
  • Menu: drag+toggle → vale na próxima busca (<30s)
  • Bot: teste roda as regras ANTES de publicar
  • locked{} inalterável pela UI
⑬ Voz (COULD)
  • Live API responde < 500ms com interrupção
  • Fallback texto sem perder contexto
  • Feature flag ON só se ①–⑦ prontas

8 Teste dos 5 minutos — se responder estas 5, você entendeu 100%

Como usar: tente responder antes de abrir. Se travar em alguma, a seção indicada resolve. Se alguma resposta aqui surpreender, o blueprint cumpriu o papel.

1 · Em que caso EXATO o bot aparece para a cliente?
zero_results === true E query ≥ 3 caracteres, no máximo 1 vez por sessão de busca (oferta, nunca pergunta em aberto). Se a nativa resolveu: silêncio total. → Estados + Tela ①
2 · Qual a diferença entre VARIAÇÃO e FLEXIBILIZOU?
VARIAÇÃO = mesmo produto, outra variante (verde escuro em vez de verde claro). FLEXIBILIZOU = uma preferência declarada foi relaxada COM PERMISSÃO (tom do verde), mas os filtros duros (orçamento, tamanho) ficam intatos — e o cartão diz o que flexibilizou. → Solver, 6 táticas
3 · De onde vem o "R$ 512 recuperados" do painel?
Do ledger append-only (W08): cada ORDER_PAID da loja chega por webhook assinado (HMAC), passa pela fila Pub/Sub e é creditado 1× (idempotência). "Recuperado" = pedido ligado a uma sessão com interação Recova. Sem esse encadeamento, o número não existe. → Esteira + Contratos
4 · O que o lojista NÃO pode customizar de jeito nenhum?
3 coisas, travadas em config: honestidade radical (NO_VALID_RECOVERY sempre disponível), filtros duros (orçamento/tamanho inegociáveis) e atribuição de receita auditável. Ele muda a VOZ do bot, nunca a HONESTIDADE. → Decisões D10 + faixa vermelha
5 · Na demo, o que é simulado e o que é real?
Simulado: só o clique final do pagamento. Real: a busca, o roteamento, a varredura do catálogo, os cartões com prova, a conversa, e TODA a esteira de eventos (webhook, HMAC, fila, ledger, painel). O pitch é: "a engenharia é real, o cartão de crédito é que é de mentira". → Decisão D7

💬 Discordou de algo aqui? O fluxo é: trazer evidência nova → reabrir a decisão específica pelo número (D#) → decidir em 1 conversa → atualizar ESTE arquivo. Preferência sem evidência não reabre decisão.
